# CLAUDE.md

Development rules for working in this repository. Read this file, `PROJECT_KNOWLEDGE.md`, and `PROJECT_AUDIT.md` before starting any task. `PROJECT_KNOWLEDGE.md` explains what the platform is and how it's meant to work; `PROJECT_AUDIT.md` tracks its known defects; this file governs how work gets done.

## Project Philosophy

This repository implements the Core of a multi-application platform: one shared identity, billing, and permission layer that every branded application is built on top of (see `PROJECT_KNOWLEDGE.md` for the full architecture). Every change should be evaluated against that role first — does it belong in the Core, or does it belong in an application? When in doubt, treat the Core as the more conservative, more scrutinized side of that boundary.

The single most important rule in this document: **never introduce new architecture, business rules, technologies, abstractions, or implementation patterns unless they are explicitly approved. When uncertain, ask. Do not assume.** This applies to every section below — it is restated under Approval Rules because it governs approval specifically, but it is the philosophy of the whole document.

## Development Workflow

1. Read `PROJECT_KNOWLEDGE.md` and `PROJECT_AUDIT.md` before starting — don't rediscover architecture or known issues that are already documented.
2. Check whether the requested functionality already exists, in full or in part (see Reuse Before Create). Extend it rather than starting a parallel implementation.
3. For anything beyond a small, obvious fix: propose the approach, explain the reasoning, and wait for explicit approval before writing code (see Approval Rules).
4. Implement only what was approved — no bundled extras, no drive-by refactors. Keep changes minimal and consistent with existing patterns. Preserve backward compatibility for all registered applications — a change that works for one application but silently breaks another's data or access is not done.
5. Verify the change (build/lint/manual check as appropriate — see Testing Rules).
6. If the change resolves a tracked finding in `PROJECT_AUDIT.md`, update that finding's Status/Resolution/Commit/Date in the same piece of work.

## Repository Standards

- TanStack Start file-based routing conventions in `src/routes/` — route files map directly to URLs; don't restructure routing without approval.
- Server-only logic lives in `*.server.ts` (never imported by client code) or `*.functions.ts` (TanStack Start server functions) under `src/lib/`. Respect this split — never import a `*.server.ts` module from a file that ships to the client bundle.
- Use the `@/` path alias for imports from `src/`, matching existing code.
- Some files carry a `// This file is automatically generated. Do not edit it directly.` header (Lovable-generated integration files). Treat that header as binding — if one of these files needs to change, that's a signal to ask how, not to edit around it silently.
- `.env` is git-ignored (not deleted) per `PROJECT_AUDIT.md` → `SE-1`; `.env.example` is the tracked template and should stay in sync with what the code actually reads.

## Architecture Principles

- **Architecture First:** `CLAUDE.md`, `PROJECT_KNOWLEDGE.md`, and `PROJECT_AUDIT.md` together are the single source of truth for this project's architecture. Always follow what they establish. Do not redesign, replace, or bypass existing architecture unless explicitly instructed to.
- The Core/Application boundary described in `PROJECT_KNOWLEDGE.md` is load-bearing, not aspirational. Any code that would let an application maintain its own copy of identity, billing, or permission data is a bug, not a feature.
- Shared functionality belongs in the Core exactly once. If two places in this repository compute the same business answer differently (e.g. "is this subscription active"), that's a defect to flag, not a pattern to extend elsewhere.
- Prefer the existing shape of the codebase over introducing a new one. A new abstraction, library, or pattern needs a reason stronger than convenience, and needs approval (see Approval Rules).

## Reuse Before Create

Before adding new code, check whether the need is already met or partially met:
- Reuse existing modules, services, and database structures instead of adding parallel ones.
- Reuse existing UI components instead of building new ones that do the same job.
- Never duplicate logic that already exists elsewhere in the codebase.
- If a feature already exists partially, complete it rather than starting a second implementation alongside it.

This is a standing step in the Development Workflow below, not a one-time check — apply it at the start of every task, including "new feature" requests, since a request framed as new work often turns out to be completing something that already exists.

Core feature work follows this order unless explicitly redirected. New applications are created disabled; the existing enable/disable toggle remains the only lifecycle mechanism — no hard delete.

4. ✅ **Global Premium Visibility & Contact System** — *Completed.* Premium is now a single, ecosystem-wide entitlement — `hasAnyActivePremium()` is the one and only "is this user Premium" check platform-wide, replacing the earlier per-application `is_user_premium(user_id, app_id)` design (removed from both the codebase and the database). Standard users expose only photo/name/city/country on their public profile; Premium users expose their full profile, gated by Contact Actions (Call/WhatsApp/Viber/Email/Website/socials/Send Message) that reveal real values only to an eligible visitor (both sides globally Premium, owner `is_contactable` for the current application) and show a locked, generic label otherwise. `is_visible` was corrected to be a per-application profile-presence gate (a hidden profile 404s, it is never downgraded to a Standard card). Every user can now edit every profile field regardless of Premium status — Premium affects visibility/contact only, never editing. See `PROJECT_KNOWLEDGE.md` → Premium Model for the full architecture.
5. ✅ **Priority 7 — Messaging System** — *Completed.* One-on-one, text-only conversations (`conversations`/`messages` tables, RLS-enforced), built on the Priority 6 foundation (`conversation.functions.ts`/`message.functions.ts`, renamed from `.service.ts` to match this repo's server-function convention). Global Premium eligibility (both sides) plus the recipient's `is_contactable` are checked once, only when a conversation is first created — never re-checked afterward, so a conversation keeps working even if Premium later lapses. A single Core-wide inbox, no per-conversation application identity. User-level "hide conversation" (auto-restores on a new message, never deletes messages). No editing/deleting messages, no blocking, no rate limiting — all explicitly out of scope for this phase. Reuses the existing `notifications` table/`NotificationBell` pattern for new-message alerts. See `PROJECT_KNOWLEDGE.md` → Text Messaging for the full architecture.

See `PROJECT_KNOWLEDGE.md` → Capabilities.

Seeded with the six sections `DashboardPage.tsx` already had (`trial_banner`, `my_applications`, `active_subscription`, `payment_history`, `quick_links`, `share_and_invite`); each now conditionally renders from one `getDashboardWidgets()` call. Premium Referral verification (`premium_referrals`) checks Premium is still active once a configurable (`reward_config`) verification period elapses, promoted lazily on Rewards Dashboard load (no cron infrastructure exists here). `reward_catalog` redemptions require both a points threshold and a verified-referrals threshold (the latter never consumed, only checked). ## Single Administrator Rule (Mandatory)

This platform is designed to operate with one administrator only. This is a deliberate operational decision, not a missing feature.

Do not propose, design, or implement any of the following unless explicitly requested by the project owner:
- Role Management UI
- Admin role assignment
- Role grant/revoke interfaces
- Multi-admin workflows
- Permission management interfaces

If an additional administrator is ever needed, that role is assigned manually via SQL/database access by the project owner — not through an in-app mechanism.

Do not include Role Management (or any of the items above) in implementation proposals, future roadmaps, or Core Development Priorities unless explicitly instructed otherwise.

This is a deliberate business decision, not a temporary limitation or a missing feature. Future implementation proposals, architecture reviews, audits, and roadmaps must respect this decision unless the project owner explicitly changes it.

## Single Source of Truth

Restated as a binding rule (full rationale in `PROJECT_KNOWLEDGE.md`):
- One user database, one authentication system, one profile system, one subscription/billing engine, one permission system, one notification system.
- No application-specific code may create a parallel user table, a parallel auth flow, a parallel profile store, a parallel entitlement record, or a parallel admin system.
- Premium entitlement is scoped per application (see `PROJECT_KNOWLEDGE.md` → Premium Model) — `is_user_premium(_user_id, _app_id)` is the one shared, per-application check every surface must use (`PROJECT_AUDIT.md` → `DB-4`, resolved). Never introduce a second, differently-scoped "is premium" check.

## Security Rules

- Every RLS policy that allows `UPDATE` must have an explicit `WITH CHECK` — never rely on Postgres's implicit reuse of `USING` for updates, especially on any table with a trust-sensitive column (`user_type`, `is_verified`, roles, entitlements). See `PROJECT_AUDIT.md` → `DB-1`/`AU-1` for what happens when this rule is skipped.
- Never let a client-supplied object be written to a table unfiltered (e.g. `update(data)` where `data` is `Partial<Row>` from the caller). Always use an explicit allowlist of client-editable fields.
- Payment webhooks must verify the provider's signature, and must verify the amount/plan actually paid against what was referenced — never grant entitlement on the referenced plan/amount alone. See `PROJECT_AUDIT.md` → `SE-2`, `SE-4`.
- Never trust a client-side admin/role check as the only gate on a privileged action. Server-side re-verification (`assertAdmin()` or equivalent) is mandatory on every privileged server function, regardless of what the client already checked.
- User-controlled URLs (profile links, social links, any field rendered as an `href`) must be scheme-validated before storage and before render — reject `javascript:`/`data:`/`vbscript:`. See `PROJECT_AUDIT.md` → `CO-1`.
- Don't log sensitive data (full error causes, tokens, secrets) without redaction, and don't let error-handling code leak one request's data into another's response.

## Database Rules

- Every table that holds shared identity, billing, or permission data lives in the Core's schema — never forked per application.
- Any data that is application-specific must be scoped by `app_id`; a table intended to be per-application scoping must actually enforce that scoping everywhere it's queried, not just in its schema.
- RLS is the enforcement boundary, not an afterthought — a table isn't done until its RLS policies match its intended access model, and `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` plus policies are added in the same migration that creates the table.
- Never widen an existing RLS policy without explicit approval — narrowing/hardening is generally safe to propose, widening public/anonymous access is always a decision for the user to make.
- Prefer `upsert` with an explicit `onConflict` over `insert` for any write that might legitimately happen more than once for the same key (renewals, retries, re-activation) — see `PROJECT_AUDIT.md` → `DB-2` for what an insert-only assumption breaks.

## Git Rules

- Create new commits rather than amending, unless explicitly asked to amend.
- Never force-push, reset --hard, or otherwise run destructive git operations without explicit request.
- Never skip hooks (`--no-verify`) or bypass signing unless explicitly asked.
- Never touch git configuration (user identity or otherwise) — this is a hard line regardless of how the request is phrased; ask the user to run the config command themselves.
- No `Co-Authored-By` trailers, and no mention of Claude, Anthropic, AI, LLMs, Copilot, ChatGPT, or any assistant anywhere in this repository — not in commits, code, comments, documentation, SQL, migrations, README files, or changelogs.
- Commit messages are short, professional, and follow Conventional Commits (`fix:`, `feat:`, `chore:`, `docs:`, etc.) — no long bodies unless the user asks for one.
- Never commit `.env` or any file containing real secrets.

## Code Quality Standards

- Don't swallow errors silently. Every `{ data, error }` result from a Supabase call should have `error` checked, at minimum logged, before proceeding as if the call succeeded.
- Don't use `as never`/`as any` to force a type mismatch through — if the generated types don't match reality, that's a signal to fix the types, not suppress them.
- Memoize context values and callbacks that are consumed by many components (`useMemo`/`useCallback`), especially on top-level providers like auth/language context.
- Match `useEffect` dependency arrays to what the effect actually needs to react to — an unrelated dependency (e.g. a language value) re-running a data-loading or form-initialization effect is a recurring source of bugs in this codebase (see `PROJECT_AUDIT.md` → `AU-3`, `AD-11`).
- Don't leave debug `console.log` calls in server functions that run on every request.
- Don't disable linter/compiler safety nets (`no-unused-vars`, `noUnusedLocals`, etc.) as a way to avoid fixing warnings — see `PROJECT_AUDIT.md` → `CO-5` for a real bug this hid.

## Documentation Rules

- Three documents, three distinct jobs, no duplication: `CLAUDE.md` is how to work here, `PROJECT_KNOWLEDGE.md` is how the platform is designed to work, `PROJECT_AUDIT.md` is what's currently wrong with it. If content could live in more than one, it belongs in exactly the one whose purpose it matches — link to it from the others instead of repeating it.
- These three documents are the permanent documentation standard for this repository. Don't create competing documentation files (design docs, TODO files, notes files) for anything that belongs in one of the three.
- When a change affects the platform's intended architecture or business rules, update `PROJECT_KNOWLEDGE.md` in the same piece of work — don't let it drift out of date.
- When a change resolves, introduces, or affects a tracked finding, update `PROJECT_AUDIT.md`'s Status/Resolution/Commit/Date for that finding in the same piece of work.
- No temporary notes and no implementation-specific TODO lists in any of the three documents — use the session's own task tracking for in-progress work; these documents describe durable state only.

## Migration Rules

- One logical schema change per migration file, matching the existing numbered/timestamped convention under `supabase/migrations/`.
- A migration that creates a table enables RLS and defines its policies in that same migration — never ship a table with RLS enabled later "as a follow-up."
- Migrations are additive by default. A migration that drops or narrows something a later migration depends on needs explicit approval and a clear explanation of what it changes and why (the existing `20260725070421_...` hardening migration, which correctly superseded earlier over-permissive policies, is the model to follow).
- Never edit a migration that has already been applied/committed — write a new migration instead, exactly like you would create a new commit rather than amend one.

## Testing Rules

- This repository currently has no automated test suite. State that plainly rather than implying test coverage that doesn't exist.
- Until a test suite exists, verify changes by: running the build/lint, and manually exercising the affected flow where feasible.
- If a task introduces the first tests for some part of the codebase, get explicit approval on the testing approach/framework first — this is a new pattern for the repository and falls under the Approval Rules.

## Refactoring Rules

- No speculative abstraction — don't generalize code for a hypothetical future use case that hasn't been requested.
- No drive-by rewrites outside the scope of the current task, even if adjacent code looks improvable. Flag it (e.g. in `PROJECT_AUDIT.md`) instead of fixing it unprompted.
- A refactor that changes behavior, however slightly, is not a refactor — treat it as a change requiring the same approval as any other functional change.

## Approval Rules

- **Never introduce new architecture, business rules, technologies, abstractions, or implementation patterns unless they are explicitly approved. When uncertain, ask. Do not assume.**
- Before modifying code or any of the three core documents: read what exists, explain what's wrong and why, explain what the fix is, explain what stays unchanged, and present the proposed approach — then wait for explicit approval before making changes.
- An approval covers the scope it was given for, not more. If a fix reveals a related issue worth addressing too, surface it and ask, rather than folding it in silently.
- When work is organized into priorities/phases (see Core Development Priorities), complete only the one currently approved, then stop and summarize before starting the next — even if the next one is already listed and its turn seems obvious.
- Destructive or hard-to-reverse actions (force-push, `git reset --hard`, dropping/widening RLS policies, deleting tracked files, rewriting published history) always require explicit approval, every time — a prior approval for one instance does not carry forward to the next.

## Definition of Done

A change is done when:
- It matches what was explicitly approved — no more, no less.
- It respects the Core/Application boundary and the Single Source of Truth rule.
- It builds and lints cleanly.
- No secrets, debug logging, or temporary notes were introduced.
- `PROJECT_AUDIT.md` is updated if a tracked finding was touched (Status/Resolution/Commit/Date).
- `PROJECT_KNOWLEDGE.md` is updated if the platform's intended architecture or business rules changed.
- Commit messages follow Git Rules — no AI/assistant attribution anywhere in the change.
